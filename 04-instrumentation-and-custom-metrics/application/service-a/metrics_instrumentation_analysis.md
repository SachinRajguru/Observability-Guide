### 1. Purpose

Service A is the primary instrumentation example in this project.

It demonstrates how an application can expose telemetry about its own behavior.

The application provides:

* HTTP request metrics;
* request duration metrics;
* active-request tracking;
* Node.js runtime metrics;
* application logs;
* distributed tracing;
* downstream service communication.

## 3. Default Node.js Metrics

The following statement enables standard process metrics:

```javascript
promClient.collectDefaultMetrics();
```

These metrics are generated by the Prometheus client library.

They can provide information about the Node.js process and runtime.

This is different from application-specific metrics.

For example:

```text
Default/runtime metric
    process memory

Custom application metric
    HTTP requests
```

Both are useful.

## 4. HTTP Request Counter

The project defines:

```javascript
const httpRequestCounter = new promClient.Counter({
  name: 'http_requests_total',
  help: 'Total number of HTTP requests received by Service A',
  labelNames: ['method', 'route', 'status_code']
});
```

The metric name:

```text
http_requests_total
```

follows the Prometheus naming convention for cumulative request counts.

The labels provide additional dimensions:

```text
method
route
status_code
```

For example:

```text
http_requests_total{
  method="GET",
  route="/healthy",
  status_code="200"
}
```

## 5. Why Counters Are Useful

A raw counter tells us the total number of observations.

PromQL can calculate rates.

Example:

```promql
rate(http_requests_total[5m])
```

This answers approximately:

> How many requests per second have been arriving during the last five minutes?

Another useful query is:

```promql
increase(http_requests_total[1h])
```

This estimates how many requests occurred during the last hour.

## 6. Gauge

The application defines:

```javascript
const activeRequestsGauge = new promClient.Gauge({
  name: 'active_requests',
  help: 'Number of HTTP requests currently being processed'
});
```

When a request begins:

```javascript
activeRequestsGauge.inc();
```

When the response finishes:

```javascript
activeRequestsGauge.dec();
```

Therefore the Gauge represents current state rather than cumulative history.

## 7. Histogram

The application records request duration:

```javascript
const requestDurationHistogram = new promClient.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.1, 0.5, 1, 2, 5]
});
```

The buckets represent:

```text
<= 0.1 seconds
<= 0.5 seconds
<= 1 second
<= 2 seconds
<= 5 seconds
```

A histogram also produces `_count` and `_sum` series.

## 8. Summary

The application also defines:

```javascript
const requestDurationSummary = new promClient.Summary({
  name: 'http_request_duration_summary_seconds',
  help: 'HTTP request duration summary in seconds',
  labelNames: ['method', 'route', 'status_code'],
  percentiles: [0.5, 0.9, 0.95, 0.99]
});
```

The configured values represent:

```text
0.50 = 50th percentile
0.90 = 90th percentile
0.95 = 95th percentile
0.99 = 99th percentile
```

For example, the 95th percentile approximates the request duration below which 95% of observed requests fall for that Summary stream.

## 9. Histogram vs Summary

| Feature                          | Histogram | Summary               |
| -------------------------------- | --------- | --------------------- |
| Buckets                          | Yes       | No                    |
| Count                            | Yes       | Yes                   |
| Sum                              | Yes       | Yes                   |
| Client-side quantiles            | No        | Yes                   |
| Aggregation across instances     | Strong    | Limited for quantiles |
| Common Prometheus latency choice | Yes       | Sometimes             |

When we operate multiple replicas and want aggregate latency percentiles, Histograms are generally the more flexible option.

## 10. Request Middleware

The middleware measures every request.

The lifecycle is:

```text
Request arrives
      |
      v
Start timer
      |
      v
Increment active request Gauge
      |
      v
Express endpoint
      |
      v
Response finishes
      |
      +---- Record Counter
      |
      +---- Observe Histogram
      |
      +---- Observe Summary
      |
      +---- Decrement Gauge
```

This allows a single middleware component to instrument all routes.

## 11. `/metrics`

The metrics endpoint is:

```javascript
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', promClient.register.contentType);
  res.end(await promClient.register.metrics());
});
```

Prometheus can scrape:

```text
http://service-a:3001/metrics
```

The response is not intended for human-friendly presentation.

It is intended for Prometheus-compatible scraping.

## 12. Manual Timing

The `/example` endpoint demonstrates manual timing.

The start time is recorded:

```javascript
const startTime = process.hrtime.bigint();
```

The operation executes:

```javascript
await new Promise((resolve) => {
  setTimeout(resolve, 100);
});
```

The duration is calculated:

```javascript
const durationSeconds =
  Number(process.hrtime.bigint() - startTime) / 1e9;
```

This is useful for understanding the basic idea behind latency measurement.

## 13. Service-to-Service Tracing

Service A calls:

```text
SERVICE_B_URI/hello
```

Example:

```text
http://b-service.dev/hello
```

The HTTP instrumentation can automatically create spans for the outgoing HTTP request.

Therefore a distributed trace can look like:

```text
Trace
|
+-- Service A
    |
    +-- HTTP GET b-service.dev/hello
            |
            +-- Service B
```

## 14. Why tracing.js must load first

The beginning of `index.js` is intentionally:

```javascript
require('dotenv').config();
require('./tracing');

const express = require('express');
const axios = require('axios');
```

The tracing SDK is initialized before Express and Axios are loaded.

This allows automatic instrumentation to hook into supported libraries.

## 15. Logs

Morgan provides HTTP access logging.

Pino provides structured application logs.

Example:

```javascript
logger.info({
  event: 'calling_service_b',
  service_b_uri: SERVICE_B_URI
});
```

Structured logs are easier for centralized logging systems to parse.

## 16. Crash Testing

The `/crash` endpoint exists only for this observability exercise.

It calls:

```javascript
process.exit(1);
```

Kubernetes sees the container process terminate and can restart the container according to the Pod restart policy.

This makes it possible to test:

```text
Application crash
       |
       v
Container exits
       |
       v
Kubernetes restarts container
       |
       v
Pod restart count increases
       |
       v
Prometheus alert
       |
       v
Alertmanager
```

Never expose an intentional crash endpoint in a real production application.

## 17. Important Learning Point

Application instrumentation is not the same thing as monitoring infrastructure.

We need several layers:

```text
Application
    |
    +---- Instrumentation
    |
    +---- Metrics endpoint
    |
    +---- Logs
    |
    +---- Trace generation
             |
             v
       Observability stack
```

This separation is fundamental to understanding modern observability.
